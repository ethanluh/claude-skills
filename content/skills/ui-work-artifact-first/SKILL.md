# UI work: artifact first

Update the visual artifact (desktop + mobile where relevant) and get
Ethan's sign-off before writing implementation code.

- Wrong order: implement, then screenshot.
- Right order: artifact → approval → implement.

This applies to new UI, layout changes, and visual redesigns alike — not
just from-scratch builds. If the request is UI-shaped at all, produce or
update the artifact first and wait for explicit approval before touching
real implementation code.

## Approximate values express intent, not literals

When Ethan gives a rough spec ("~2 inches", "swap launch and remix"),
treat it as intent, not a literal instruction to satisfy exactly.
"~2 inches" means "big enough to fill the screen" — satisfy the goal, not
the number. If a referent is ambiguous, confirm which elements before
building rather than guessing.
