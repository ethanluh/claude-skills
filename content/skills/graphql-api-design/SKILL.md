# graphql-api-design — demand-oriented schema, precise fields, single-purpose mutations, pagination

Source: [[graphql-demand-oriented-schema-design]] (Apollo GraphOS schema-design
guide + graphql.org best practices).

## Core inversion

A GraphQL schema is a product surface for client developers, not a mirror of
your database or service layer. Design **from client use cases inward**, not
from the data model outward. If you can trace a field back to "that's just
what the `users` table has" rather than "a client needs this," that's a
smell.

## Checklist

**Schema direction**
- [ ] Every type/field traces to an actual client use case, not to a table or
      internal service column.
- [ ] The schema does not leak implementation details of any one backend
      service.
- [ ] The schema is not shaped around one particular client — it's a shared
      contract, not that client's private API.
- [ ] Schema was NOT autogenerated wholesale from a database/service layer.
      That's fast but exposes unrequested fields, creates accidental client
      dependencies on incidental structure, and turns future changes into
      breaking changes by surprise.

**Field precision**
- [ ] No single query with a pile of optional/nullable arguments standing in
      for several different lookups (e.g. `user(id: ID, username: String)`).
      Split into precise, narrowly-scoped queries (`userById`,
      `userByUsername`) instead — costs a slightly bigger schema, saves
      runtime validation logic and gives clearer per-query observability.
- [ ] Nullability on a field reflects a real semantic ("this can genuinely be
      absent"), not laziness about validation.

**Mutations**
- [ ] Mutations are single-purpose, not broad "update the whole object"
      operations. Reject `updateAccount(input: AccountInput)` covering every
      field; prefer `updateFullName`, `changeBillingAddress`, etc.
- [ ] Each mutation's side effects are enumerable up front — if you can't say
      what changed and what it triggers without inspecting which subset of
      input fields were set, split it further.
- [ ] This is the same discipline as narrow REST PATCH design — narrow,
      explicit operations beat generic "update anything" endpoints there too.

**Pagination**
- [ ] Pagination is applied deliberately per list field, not reflexively on
      every list (a fixed-size embedded list doesn't need it).
- [ ] Once a style is chosen (cursor-based vs. offset-based), it's enforced
      **uniformly** across the whole schema — clients should never have to
      special-case how one list field paginates versus another.

**Governance (needed from day one, not retrofitted)**
- [ ] Naming conventions are decided and applied consistently.
- [ ] Field-level documentation exists for anything non-obvious.
- [ ] There's an explicit process for what counts as a breaking change
      (removing/renaming a field, changing nullability, changing a
      mutation's input shape) before the schema ships to any client.

## Contrast with REST

GraphQL pushes resource-shape decisions to query time — a client picks
exactly the fields it wants. That flexibility is precisely why schema
governance (naming, nullability, mutation granularity) has to be **stricter
up front** than in REST, where the resource shape is fixed by the endpoint
and a bad shape is a smaller, localized problem. For REST-specific
checklist criteria (resource-noun modeling, verb semantics, versioning,
error envelopes), see the `rest-api-design` skill instead.
